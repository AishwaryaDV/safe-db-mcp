## Shared conventions for both repos

**Tooling**

- Python 3.11 or newer, `pyproject.toml`, `ruff` for lint and format, `pytest`, type hints everywhere, `pydantic` models for every tool input, tool output and API body.
- Backend: FastAPI. Frontend: Next.js (App Router, TypeScript) with Tailwind in `web/`.
- Config: `config.yaml` for non-secret settings, `.env` for secrets, a committed `.env.example`, loaded with `pydantic-settings`.
- A `Makefile` with `setup`, `test`, `eval`, `run`, `lint`.
- Structured JSON logs. MIT licence. Never commit `data/raw`, `.env`, or databases.
- No LangChain, LlamaIndex or similar frameworks.

**`llm_client.py` contract**

```python
class LLMResult(BaseModel):
    text: str | None
    tool_calls: list[ToolCall]          # name + arguments
    usage: Usage                        # input_tokens, output_tokens
    latency_ms: int
    backend: str                        # claude_sdk | gemini
    model: str
    cached: bool

class LLMClient:
    def generate(self, messages, tools=None, response_schema=None, temperature=0.0) -> LLMResult: ...
```

- **Backends:** `claude_sdk` (development only; uses the owner's local Claude Code login through the Claude Agent SDK, no API credits) and `gemini` (free tier, key in `GEMINI_API_KEY`). Choose with `LLM_BACKEND`.
- **Fallback:** if `claude_sdk` raises or is unavailable, retry once on `gemini` and log the fallback.
- **Modes (`LLM_MODE`):** `live` (call the model), `record` (call and save), `replay` (read only from cache; a cache miss raises an error that says to re-record). CI always runs `replay`.
- **Cache key:** SHA-256 of model name, messages, tool definitions, response schema and temperature. Cache files live in `llm_cache/` and only the files needed by the committed baseline run are committed.
- **Quota guard:** count requests per day in the `llm_calls` table and refuse new live calls above `DAILY_LLM_BUDGET` (default 200) with a clear error. The Gemini free-tier limits are published inconsistently, so keep the budget below the conservative figure and check the current docs.
- **Call log:** every call writes a row to `llm_calls` (time, backend, model, latency, input and output tokens, cached, error, run id).
- **Tool calling:** translate tool definitions into each backend's function-calling format inside the client; the rest of the code only sees the neutral `tools` list.

**Tests and CI (GitHub Actions)**

- Markers: `unit`, `integration`, `live_llm`. CI runs everything except `live_llm`.
- Jobs: lint, unit and integration tests, the repo-specific gate (safety tests or retrieval metrics), and the eval in `replay` mode with a regression check.
- A manual `workflow_dispatch` job runs a small live smoke test with the `GEMINI_API_KEY` secret.

## Goal and acceptance

An MCP server that lets Claude Desktop or Cursor ask questions of SQLite databases, with every query validated, limited and logged, plus an eval harness that measures how accurately a model answers benchmark questions using the server's tools.

**Acceptance, all must be true:**

- [ ] The server runs over stdio and works in MCP Inspector and in Claude Desktop or Cursor
- [ ] Four tools, one resource and one prompt exist exactly as specified below
- [ ] Every item in the hostile-query list is blocked or limited as specified, and the data files are byte-identical after the suite runs
- [ ] Every tool call produces an audit row
- [ ] The eval runs the 50-question slice through the real MCP server using an MCP client, and reports execution accuracy, first-try valid rate, recovery rate, blocked-query rate, tool calls and latency
- [ ] Two experiments are reported: sample rows on or off, and error hints on or off
- [ ] `replay` mode reproduces a recorded run's metrics exactly
- [ ] Dashboard has an audit log page, an eval results page and a try-a-question page, deployed with daily caps
- [ ] README meets the shared standard

**Out of scope:** any write capability, even behind a flag; the server calling an LLM; user accounts; Postgres or MySQL (stretch only); LangChain SQL agents.

## MCP tool contracts

Use the official Python MCP SDK. Transport: stdio. Entry point: `safedb-mcp --config config.yaml`. Confirm the SDK's current API before writing `server.py`.

**`list_databases`**

- Input: none
- Output: `{databases: [{name, description, table_count}]}`

**`describe_schema`**

- Input: `{database: str, table?: str, sample_rows?: int (0 to 5, default 3)}`
- Output: `{database, tables: [{name, row_count, columns: [{name, type, primary_key, not_null}], foreign_keys: [{column, ref_table, ref_column}], sample_rows: [[...]]}]}`
- Sample cell values longer than 80 characters are cut with an ellipsis. With `sample_rows=0` the field is omitted.

**`run_query`**

- Input: `{database: str, sql: str, max_rows?: int}`
- Success: `{ok: true, columns: [str], rows: [[...]], row_count: int, truncated: bool, elapsed_ms: int}`
- Failure: `{ok: false, error_type, message, hint?}`
- `max_rows` defaults to 100 and is capped at `max_rows_cap`. Cells longer than `max_cell_chars` are cut.

**`explain_query`**

- Input: `{database: str, sql: str}`
- Output: `{ok: true, plan: [str]}` or the same failure shape. The SQL goes through the same validation, and the query is never executed.

**Error types**

| `error_type` | When | Hint content |
| --- | --- | --- |
| `blocked` | Validation rejected the SQL | What is allowed: one `SELECT` statement only |
| `syntax` | The parser or SQLite reported a syntax error | The parser's message and position |
| `unknown_object` | Unknown database, table or column | Up to 3 closest real names (use `difflib`), and for a table also its columns |
| `timeout` | Ran longer than `timeout_s` | Suggest adding filters or `LIMIT`, or simplifying joins |
| `too_large` | SQL longer than `max_sql_chars` | Suggest a shorter query |
| `internal` | Anything else | None; log the exception, return a generic message |

With hints switched off (an eval experiment, `HINTS=off`), return only `message`.

**Resource.** `schema://{database}` returns the full schema as markdown text (tables, columns, keys), for clients that attach resources.

**Prompt.** `analyst` with argument `database`. Its text is a short list of working rules: call `describe_schema` before writing SQL; quote identifiers that need it; always limit rows; state assumptions in the answer; if the question is ambiguous, ask one clarifying question instead of guessing; never attempt to change data.

**Tool descriptions.** Keep all description strings in `tool_descriptions.py`. Each is at most three sentences and says when to use the tool. Record a hash of this file in every eval run, because wording changes affect accuracy.

**Rules:** the server makes no LLM calls, has no write tools, and returns plain data only. Return results as structured content and also as a text rendering.

## Safety layer

Build `validate_sql` and the executor as independent layers, in this order. Confirm exact API names in the Python `sqlite3` and `sqlglot` documentation before coding.

1. **Size check.** Reject if longer than `max_sql_chars` (`too_large`).
2. **Parse.** Parse with `sqlglot` using the SQLite dialect. Parse failure is `syntax`.
3. **Exactly one statement.** More than one is `blocked`.
4. **Allow-list the statement.** The root must be a `SELECT` (including `WITH ... SELECT` and set operations such as `UNION`). Walk the tree and reject any node that is not part of a read query, including any command, pragma, attach, insert, update, delete, create, drop, alter or vacuum node.
5. **Deny dangerous functions** by name, at minimum `load_extension`, `readfile`, `writefile`, `edit`.
6. **Read-only connection.** Open with a `file:` URI and `mode=ro`, then `PRAGMA query_only = ON`. Disable extension loading on the connection.
7. **Authorizer.** Register an authorizer callback that allows only read-type actions (select, read, permitted functions, recursive) and denies everything else. This is the second wall if a statement ever slips past the parser.
8. **Timeout.** Register a progress handler that checks a monotonic clock every ~1000 VM steps and aborts after `timeout_s`. Map the abort to `timeout`.
9. **Row and cell caps.** Fetch `max_rows + 1` rows, return `max_rows`, set `truncated`. Cut long cells.
10. **One connection per call,** closed afterwards. One in-flight query per database at a time.
11. **Audit.** Write the audit row on a separate writable connection, in a `finally` block, so blocked and failed calls are logged too.

## Audit log and API

**Audit table** (in `audit.sqlite`, a file separate from every data database):

```sql
CREATE TABLE audit_log (
  id INTEGER PRIMARY KEY,
  ts TEXT NOT NULL,              -- ISO 8601 UTC
  source TEXT NOT NULL,          -- mcp | api | eval
  tool TEXT NOT NULL,            -- list_databases | describe_schema | run_query | explain_query
  database TEXT,
  sql TEXT,
  sql_hash TEXT,
  status TEXT NOT NULL,          -- ok | blocked | error | timeout
  error_type TEXT,
  reason TEXT,
  row_count INTEGER,
  truncated INTEGER,
  elapsed_ms INTEGER,
  run_id TEXT                    -- set for eval runs
);
CREATE INDEX audit_ts ON audit_log (ts);
CREATE INDEX audit_status ON audit_log (status);
```

The `llm_calls` table from the shared conventions lives in the same file.

**API (FastAPI).** Browser input never contains raw SQL.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/health` | Liveness |
| `GET /api/audit?status=&database=&limit=&before_id=` | Paged audit rows, newest first |
| `GET /api/eval/runs` | List runs with config and headline metrics |
| `GET /api/eval/runs/{run_id}` | Full metrics for one run |
| `GET /api/eval/runs/{run_id}/questions?result=` | Per-question records, filter by match or mismatch |
| `GET /api/examples` | Cached example questions and their recorded answers |
| `POST /api/ask` `{database, question}` | Runs `agent.py`; streams server-sent events: `tool_call`, `tool_result`, `final` |

**Limits on `/api/ask`:** 10 requests per visitor per day (by IP hash), a global daily cap below the LLM budget, and cached answers for the example questions. When a cap is hit return HTTP 429 with a friendly message and the example answers.

## Eval harness

**Commands**

- `python -m eval.build_slice`: picks the 50 questions with a fixed seed, computes gold results, writes `slice.jsonl`.
- `python -m eval.run_eval --split tune|holdout --config eval/configs/baseline.yaml --mode live|record|replay`
- `python -m eval.score --run <run_id>`: recomputes metrics from a saved run.

**Agent loop (`agent.py`)**

1. Start the MCP server as a subprocess and connect with the Python MCP client over stdio.
2. List the server's tools and convert them to the `llm_client` tool format.
3. Fetch the `analyst` prompt through MCP and use it as the system prompt, with the database name filled in.
4. Send the question. Loop: if the model calls a tool, forward the call through the MCP client and append the result; stop when the model replies without a tool call or after 5 tool calls.
5. The final SQL is the last `run_query` call that returned `ok: true`. If there is none, the question fails with reason `no_successful_query`.
6. Temperature 0. Never include `gold_sql` or `gold_result` anywhere in the conversation.

**Per-question record** (`results/<run_id>/questions.jsonl`)

```json
{"id": "q007", "steps": [{"tool": "run_query", "args": {}, "ok": false, "error_type": "unknown_object"}], "final_sql": "...", "match": true, "first_try_valid": false, "recovered": true, "blocked_count": 0, "tool_calls": 3, "latency_ms": 4120, "tokens_in": 2210, "tokens_out": 180, "backend": "gemini", "model": "..."}
```

**Run record** (`results/<run_id>/run.json`): config, split, seed, git SHA, hash of `tool_descriptions.py`, backend and model, date, headline metrics.

**Metrics**

| Metric | Definition |
| --- | --- |
| Execution accuracy | matches / questions |
| First-try valid rate | questions whose first `run_query` returned `ok: true` / questions |
| Recovery rate | questions with a failed first query that ended in a match / questions with a failed first query |
| Blocked-query rate | blocked attempts / all `run_query` attempts |
| Tool calls and latency | mean and 95th percentile |
| Tokens | mean input and output per question |

Also report accuracy by difficulty.

**Experiments** (each is a config file, run on `tune`, then confirmed once on `holdout`)

1. `sample_rows`: 3 vs 0 in `describe_schema`
2. `hints`: on vs off in error responses

Produce one comparison table from `run.json` files with `python -m eval.compare`. Run `holdout` once, at the end, with the chosen settings. Never tune on it.

**Ambiguity set.** Run `ambiguity.jsonl` through the same loop and save the transcripts. The owner scores each as good (asked a clarifying question or stated an assumption) or bad in `ambiguity_scores.csv`; a script reports the counts.

**Free-tier budget.** Before a live or record run, print the maximum number of requests it could use (questions times 6) and the remaining daily budget. Refuse to start if it would exceed the budget unless `--force` is given. Every live response is cached.

**Replay and CI.** The baseline run's cache and `eval/baseline.json` are committed. CI runs `--mode replay` on the tune split and fails if accuracy is more than 3 points below `baseline.json`, or if a cache miss occurs (the message must say to re-record). Replay must reproduce the recorded metrics exactly.

**`/audit`**

- Table: time, source, tool, database, SQL (monospace, truncated with expand), status, reason, rows, milliseconds.
- Filters: status (all, ok, blocked, error, timeout) and database. Newest first, load more at the bottom.
- Blocked rows get a distinct colour and an icon (do not rely on colour alone).
- A summary strip at the top: totals by status for the last 24 hours.

**`/eval`**

- Run picker (default: latest holdout run). Headline metric cards.
- Experiment comparison table (the two experiments, side by side).
- Per-question table with filter for mismatches. Clicking a row opens the question, each tool call and SQL attempt, the final result, and the gold result next to it.
- Gold SQL is shown here only, never in any model request.

**`/try`**

- Database picker, question box, 4 example question buttons that return cached answers instantly.
- Running a question shows each step as it streams: the tool call, the SQL, the result table, the final answer.
- Remaining questions today. A friendly 429 state that points to the cached examples.
- A visible note that queries are read-only, limited and logged, with a link to `/audit`.

**Loading and error states** for every page. No raw SQL input anywhere in the browser.

**What a first look at the READMEs found (starting point only; confirm everything in the code)**

- **SQLite is not a gap.** DBHub's README lists SQLite among its supported databases, and `mcp-sqlite-readonly` is a SQLite-only server. Do not present SQLite support as a difference.
- **`mcp-sqlite-readonly`** (a hardened fork of `mcp-sqlite`): its page describes opening the database with the read-only flag, an allow-list of SELECT, EXPLAIN and WITH, a block-list (INSERT, UPDATE, DELETE, DROP, ATTACH, PRAGMA), comment stripping, per-statement validation, and parameterised values. It exposes `db_info`, `list_tables`, `get_table_schema`, `read_records` and `query`. Its README does not mention an authorizer callback, timeouts, an audit log, a published test table or accuracy measurement. That is not proof it lacks them, because only the README was read. Check its code.
- **DBHub:** README names read-only mode, row limiting and query timeout, with no detail on SQL validation.
